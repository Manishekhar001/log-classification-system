Foundation — Chapter 1

What is a Log?

Understanding the raw material this entire project is built around.

When software runs, it constantly writes notes about what it is doing. These notes are called logs. Every event — a user logging in, a file being saved, a server crashing, a security threat being detected — gets written down automatically.

Think of a log as a flight recorder on an airplane. The pilots don't manually write notes. The plane records everything automatically. If something goes wrong, you look at the recorder to understand what happened.

Anatomy of a single log entry — three parts: when, where, and what.

Why do logs exist?

In production software — real systems serving real users — you cannot pause the program and inspect it like you would in a debugger. If something fails at 3 AM, the only evidence left is what the system wrote down while it was happening. Logs are that evidence.

  • Monitoring — Is the system healthy right now?
  • Alerting — Did something critical just happen?
  • Debugging — Why did this specific request fail?
  • Auditing — Who did what and when?
  • Capacity planning — Is memory or CPU running out?
The Scale Problem
A medium company running 6 software systems generates millions of log lines per day. No human can read millions of lines. You need a machine to read them and say: "this one is a security threat, this one is routine, this one is a broken workflow." That is exactly what this project does.

Project Overview

Log Classification System

Given a log message and the system it came from, automatically decide what type of event it represents — so the right team can act on it immediately.

Input → Output

The system takes (source, log_message) and returns (label, confidence).

The Training Data

The dataset has 2,410 rows of synthetic (artificially generated) logs. Why synthetic? Because real logs contain sensitive information like real IPs, user IDs, and internal system names. The columns are:

ColumnExamplePurpose
timestamp2025-06-01 10:32:14When the log occurred
sourceModernCRMWhich system generated it
log_messageUser 12345 logged in.The actual log text
target_labelUser ActionThe correct category (used for training)
complexityregex or bertWhich pipeline stage should handle this row

Architecture — Chapter 4

The Three-Stage Pipeline

Core Design Question
Why not just use one model for everything? Because no single approach works for all log types. Logs are not a uniform data type — some are templated machine output, some are structured but variable, some are human-written narrative. Each needs a fundamentally different strategy.

Stage 1 — Regex

When: Simple, templated logs that always follow the same pattern.

Why: O(1), deterministic, zero ML overhead. Confidence always 1.0.

Example: User 12345 logged in.

Cost: near zero

Stage 2 — BERT (MiniLM)

When: Machine-generated logs with too many variations for regex.

Why: Understands semantic meaning from embeddings. Handles variation.

Example: GET /v2/servers HTTP/1.1 200

Cost: local inference, fast

Stage 3 — LLM (Groq)

When: LegacyCRM only. Human-written narrative logs.

Why: Only 7 training examples exist — can't train a classifier. LLM has language understanding baked in.

Example: Case escalation failed because agent inactive.

Cost: API call, slowest

Unclassified — Fallback

When: All stages fail, message too short, or BERT confidence below threshold.

Why: Admitting uncertainty is better than a wrong label.

Example: asdfghjkl

Confidence: 0.0

Complete pipeline routing flowchart. Regex runs first for all sources. LegacyCRM routes to LLM. Everything else routes to BERT.
